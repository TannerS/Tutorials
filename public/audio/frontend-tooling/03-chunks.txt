What the Bundler Actually Emits. Frontend Tooling, lesson 3.

Every other lesson tells you how to split code. This one tells you what comes out the other side ,  because "the bundle" is not a file, and most of the confusion about lazy loading is really confusion about chunks. The numbers throughout are from a real production build of this site: 458 source files, 428 of them lazy-loaded routes. There Is No app.js. Real output ,  the built index.html references exactly one module. script element. ...while the build emitted 522 .js files totalling 23  megabytes. A chunk is just a .js file the bundler decided to emit. Nothing more exotic than that. There are three kinds, and knowing which is which explains everything else: A table follows, with 3 rows. Kind: Entry. What it is: The one index.html points at. Your app shell, router, React.. When it loads: Always, first, before anything renders. Kind: Async. What it is: One per dynamic import split point.. When it loads: Only when that dynamic import actually runs. Kind: Shared. What it is: Code reachable from several chunks, factored out. You never wrote these files.. When it loads: When the first chunk that needs it loads. Cached for the rest. Aside. Chunks are not 1:1 with your files. 458 source files in, 522 chunks out. And the output is not only your code ,  the two largest chunks in this build are the TypeScript compiler (3,386  kilobytes) and Sass (3,243  kilobytes), both pulled in by one interactive playground page. All chunks together = your code plus every library it actually reaches, minus whatever tree shaking proved unreachable. That is how 11  megabytes of source becomes 23  megabytes of output. How It Decides What Goes Where. Two rules, applied in order. Rule 1 ,  every dynamic import is a forced split point. This is not a heuristic. A dynamic import must become its own file, or it could not be deferred. 428 lazy routes guarantee at least 428 async chunks. Rule 2 ,  a module reachable from more than one chunk gets extracted. The bundler builds the whole module graph, then asks of each module: which chunks can reach this? Modules with the same answer get grouped into one shared chunk. Real output ,  why rule 2 matters. Code example on screen. Reachable from one chunk only  becomes  inlined into it. Reachable from many  becomes  pulled out. You can override the grouping (manualChunks in Vite, optimization.splitChunks in Webpack), but the default is usually right and manual grouping is easy to get wrong. How One Chunk Loads Another. Two mechanisms, both boring once you see them. First, the bundler rewrites your source path into the output filename at build time. You write this: Your source. Code example on screen. Real output ,  the same line, as shipped. Ju = lazy(() =  h(() =  import(`./Advanced-vLtJorqy.js`), __vite__mapDeps(...))). The source path is GONE. The emitted filename is baked in as a literal. string. There are 428 of these in the entry chunk ,  one per lazy route. So "how does it know where to look" is answered at build time, not runtime. At runtime it is a plain native dynamic import: the browser fetches that U R L, evaluates it as a module, hands back the exports. No framework magic. Second, each chunk declares its own dependencies with ordinary static imports, and the browser's module loader walks the graph itself: Real output ,  the top of one lesson chunk. from "./index-DUJ5Ntuj.js"  - the entry chunk; already loaded, free. from "./LessonLayout-*.js"  - shared. from "./CodeBlock-*.js"  - shared. from "./FlowChart-*.js"  - shared, and it pulls in mermaid.... ...which is why navigating to one lesson fetched 30 files, not 1. Diagram: One navigation, from click to rendered page. Aside. Why the 30 files do not waterfall. That h(...) wrapper with __vite__mapDeps is Vite's preload helper. It injects link element tags for the dependency list it already knows about, so those files are fetched in parallel rather than being discovered one level at a time. Without it you would pay a round trip per level of the import graph. Chunks Without Lazy Loading. Splitting and deferring are two different things, and you can have the first without the second. The distinction worth keeping. Many things produce chunks ,  manualChunks, multiple entry points, workers, C S S splitting. Only dynamic import makes a chunk optional. Manual chunks buy you parallel downloads and, in principle, better caching ,  but the browser still downloads all of them before first paint. If your goal is "do not ship what nobody visits", a split point is the only tool that achieves it. Content Hashes, and the Cascade That Defeats Them. The -vLtJorqy in Advanced-vLtJorqy.js is a hash of the file's contents. Same content  becomes  same filename  becomes  the browser reuses its cached copy. Changed content  becomes  new filename  becomes  it fetches. That is how you cache JavaScript for a year and still never serve a stale file. The usual promise is that editing one page invalidates one chunk. Test it before you believe it: Real output ,  edit ONE line in ONE lesson, rebuild, diff the filenames. chunks whose filename changed: 495. chunks whose filename survived: 27. total: 522 Aside. Why almost everything changed. A hash cascade. Every lesson chunk statically imports the entry chunk. Editing one lesson changed the entry chunk's contents, so its hash changed, so the import line inside every chunk that references it changed, so their hashes changed too. The invalidation propagates up the dependency graph to everything downstream. The fix is to make the widely-depended-on code stable ,  split framework and vendor code into their own chunks that rarely change, so a content edit cannot reach them. Until you do, treat "content hashing gives me fine-grained caching" as an assumption to verify, not a property you get for free. Diff the filenames across two builds; it takes a minute and the answer is frequently humbling. What to Take Away. The model, compressed. Code example on screen.
